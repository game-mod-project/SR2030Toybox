# 11. 게임의 안쪽 — ToyBox 가 읽고 부르는 것

조사 기준: Steam appid `2093410`, build `21347933`(게임 12.1.1360), `SupremeRuler2030.exe` 15,494,144 바이트, PE TimeDateStamp `0x695377b6`.
**이 문서의 RVA 는 모두 이 빌드의 것이다.** 게임이 업데이트되면 `uv run srkit locate` 로 다시 본다.

표기: **[확인: 정적]** 실행 파일의 명령을 직접 읽었다 · **[확인: 실행]** 화면 밖에서 띄운 게임의 메모리를 읽어 봤다 ·
**[확인: 게임]** 게임 화면에서 봤다 · **[추정]** 정황으로 판단했다.

조사 방법: 실행 파일을 읽어 MSVC 의 `dumpbin /disasm` 과 Python 으로 봤고(정적), 검증 도구가 띄운 게임의 메모리를 밖에서 읽기만 했다(실행).
분석에 쓴 스크립트와 디스어셈블리는 저장소에 넣지 않았다.

## 명령 처리 함수

게임 설정 창(`Ctrl+Shift+S`)의 입력줄에 넣은 한 줄을 처리하는 함수다. 치트 문자열 91개를 모두 이 함수가 참조한다 [확인: 정적].

- RVA `0x522330` – `0x5284fd` (25,037 바이트). 큰 함수라 함수 표(`.pdata`)에는 조각 11개로 나뉘어 있고 chained unwind 로 묶인다.
- `void f(void *this /*RCX*/, const char *line /*RDX*/)`. `line` 은 `cheat ` 까지 포함한 입력줄 전체. 길이 인자와 반환값은 없다.
- 부르는 곳은 `.text` 전체에서 **`0x6649af` 한 곳**이다. 바로 앞에서 `lea rcx,[0x1764310]` — `this` 는 정적 전역 객체의 주소 그 자체다.
- 인자 없는 치트 66개는 `strcmp`(줄 전체가 같아야 한다), 인자를 받는 25개는 `strstr` 로 맞춘 뒤 **마지막 공백 뒤**를 정수로 읽는다. 모두 소문자여야 한다.
- 머리에서 검사하는 것은 멀티플레이 표시 하나다. **게임이 진행 중인지는 검사하지 않고** 플레이어 포인터를 그대로 따라간다 — 게임 밖에서 부르면 안 된다.
- 치트 허용 비트의 검사는 함수 안 `0x522b3e` 한 곳이고, 그 앞에 있는 것(`cheat allowcheats`, `cheat devcheat`, `output…` 등)은 비트 없이도 된다.
- 게임의 메시지 루프와 창 프로시저, 프레임 갱신이 한 스레드에서 번갈아 돈다. ToyBox 는 창 프로시저 안의 타이머에서 이 함수를 부른다.
  날짜를 넘기는 계산이 그 스레드에서 도는지, 게임이 자기 호출의 앞뒤로 무엇을 잠그는지는 보지 않았다.

ToyBox 가 창 프로시저 안의 타이머에서 이 함수를 불렀을 때 **[확인: 게임 · 실행]**: `cheat allowcheats` 로 치트 허용 비트가 0 → 1,
`cheat georgew` 로 메모리의 국고가 14.43 B → 24.43 B. 게임의 설정 창은 뜨지 않는다. 지역 번호를 받는 치트 여덟 개와 `cheat treaty` 도
이 길로 넘겨 효과를 봤다([10](10-toybox.md)의 H4 ~ H8).

- **열려 있던 패널의 숫자는 스스로 다시 그려지지 않는다.** 일시 정지 중에 직접 부른 뒤 3초 · 9초가 지나도 재무 패널의 국고는 옛 값이었고,
  그 패널 안을 누르거나 패널을 다시 열면 새 값이 됐다. 시간이 "매우 느림"으로 흐르는 중에도 같았다 — 실제 41초(게임 시간 3시간) 동안 옛 값이었고
  게임의 일시 정지 단추를 누른 뒤에 새 값이 됐다([10](10-toybox.md)의 H15. 날짜가 넘어갈 때는 보지 못했다). 게임이 자기 호출 뒤에 하는 일(입력란 비우기와 `0xc06890` 호출 — 인자가
  처리기의 지역 변수라 무엇인지 모른다)을 ToyBox 는 하지 않는다. 글쇠 방식에서는 설정 창이 열렸다 닫히며 패널이 다시 그려졌다.

## 값의 흐름 [확인: 실행]

| 때 | 프로그램 상태 | 모드 상태 | 플레이어 포인터 | 치트 비트 |
|---|---|---|---|---|
| 뜨는 중 · 메인 메뉴 | 3 | 1 | NULL | 0 |
| 로비(샌드박스) | 3 | 1 | NULL (인덱스는 이미 차 있다) | 0 |
| 로비(캠페인) | 3 | 1 | **있다**(지역 객체의 상태 3, 국고 0) | 0 |
| "시작"을 누르고 0.05 ~ 0.1초 뒤 | 3 | 1 | 있다 | 0 |
| 그 0.8 ~ 1.3초 뒤 ~ 게임 안 (게임 화면은 0.3 ~ 0.7초 더 뒤에 뜬다) | 1 | 2 | 있다 | 0 |
| 게임의 설정 창 · 게임 메뉴가 열려 있을 때 | 1 | 2 | 그대로 | 그대로 |
| `cheat allowcheats` 뒤 | 1 | 2 | 그대로 | 1 |
| `cheat becomeregion <번호>` 뒤 | 1 | 2 | 그 지역으로 바뀐다 | 1 |
| 게임에서 메인 메뉴로 나온 뒤 | 3 | 1 | NULL (인덱스는 낡은 값이 남는다) | 0 |

- ToyBox 의 "진행 중" 판정: `모드 상태 == 2 && 프로그램 상태 == 1 && 플레이어 포인터 != NULL`, 그리고 읽은 값들이 서로 맞을 것
  (표[인덱스] == 포인터, 객체[+4] == 인덱스, 0 < 객체[+8] < 12900, 객체[+0] != 0).
- 치트 허용은 메뉴로 나오면 꺼진다. ToyBox 는 명령마다 비트를 보고, 꺼져 있으면 `cheat allowcheats` 를 먼저 넘긴다.
- 포인터만으로는 진행 중인지 알 수 없다(캠페인의 로비, "시작" 직후). 상태 둘을 함께 본다.
- 불러오는 동안 값이 "진행 중"이 된 뒤 게임 화면이 뜨기까지는 이 PC 에서 0.3 ~ 0.7초였고, 그동안 게임 창이 메시지에 응답하지 않았다.
  그 사이에 치트가 듣는지는 눌러 볼 수 없었다([10](10-toybox.md)의 H19).
- 메뉴로 나갔다 다시 시작한 판에서는 치트 허용 비트가 0 으로 돌아와 있고, 포인터는 새 값이다.
- ToyBox 의 나라 목록은 지역 표에서 상태가 2 또는 3 인 것만 올린다(이번 판에 실제로 있는 나라).

## 주소를 찾는 법 (`locate`)

ToyBox 는 주소를 코드에 적어 두지 않는다. 게임이 뜰 때 올라와 있는 실행 파일에서 찾는다(`native/srtoybox/locate.cpp`).
같은 코드를 `uv run srkit locate` 가 설치된 파일에 대고 돌린다. 찾는 길은 둘이다.

### 새 찾기 — 게임 상태를 읽는 전역 일곱 (3단계 1부터)

**내장 치트와 무관하다.** 치트 문자열도 치트 명령 처리 함수의 코드도 쓰지 않는다 — 게임이 업데이트로 치트를 없애도 ToyBox 는 게임을 읽는다
(사용자의 요구, 2026-10-09: 모드의 모든 기능은 게임의 내장 치트와 완전히 별도로 동작한다).

- **서명**(`native/srtoybox/sigs.h`)은 명령 몇 개의 바이트 꼴이다. `[rip]` 은 읽어 낼 주소(4바이트 rip 상대 거리)이고, `[rip+1]` · `[rip+4]` 는
  그 4바이트 뒤에 상수 1 · 4바이트가 더 있고 명령이 끝난다는 뜻이다. `?` 는 아무 바이트다.
- 서명은 실행 구역 전체에서 **정확히 한 번** 맞을 때만 "맞았다"다. 한 번도 안 맞거나 두 번 이상 맞으면 맞지 않은 것이다.
- 찾을 것마다 **서로 다른 함수에서 뽑은 서명 셋**을 둔다. **둘 이상이 맞고, 맞은 것이 모두 같은 주소**를 내야 "찾았다"다.
  값이 갈리면 못 찾은 것이다 — 다수결로 고르지 않는다.
- 일곱 가운데 하나라도 못 찾으면 ToyBox 는 게임을 읽지 못한다(내장 치트로 도는 기능은 글쇠 방식으로 동작한다).
- 찾은 주소는 쓸 수 있는 자료 구역(`.data`) 안이어야 하고 서로 겹치지 않아야 한다(3단계 1 (나)부터). 아니면 서명들이 서로 맞아도 못 찾은 것이다.

- [확인: 정적] 서명 21개가 저마다 실행 구역(12.8 MB)에 한 번만 맞고, 맞은 자리가 모두 치트 명령 처리 함수(`0x522330` – `0x5284fd`) 밖이며,
  읽어 낸 주소가 위 "전역과 필드"의 값과 같다. 자동 테스트가 설치된 실행 파일에서 이것을 보고, 치트 코드에서 읽은 값(2단계의 방식)과도 대조한다
  (`tests/test_toybox_game.py`, `tests/toybox_cheat_oracle.py` — 치트 코드를 보는 것은 테스트뿐이다).
- 서명을 맞추는 데 설치된 파일에서 24 ms 가 걸렸다(`uv run srkit locate`. 실행 구역을 한 번 훑는다). **올라와 있는 게임에서도 21개가 모두 맞는다** [확인: 실행] —
  화면 밖에서 띄운 게임과 Steam 으로 띄운 게임(Steam 오버레이의 훅이 함께 돈다)의 로그에 `게임 상태를 읽습니다 (서명 21개 가운데 21개, 31 ms)`.
  게임 안에서 잰 시간은 16 ~ 31 ms 였다(네 번. 시계의 눈금이 16 ms 쯤이다) — [10](10-toybox.md)의 V0.
- 서명의 최소 조건은 명령 셋 · 정해진 바이트 여덟 개 이상이다(`srkit sig-mine` 이 그보다 짧은 것은 내지 않는다). 게임 진입의 두 서명만 예외다 —
  명령 둘(`mov [모드 상태],2` / `mov [프로그램 상태],1`)이고, 2단계부터 쓰던 꼴이다.
- 지역 객체 안의 자리(`+0` `+4` `+8`)는 서명으로 찾지 않는다. 읽을 때마다 "서로 맞을 것"으로 거른다(위 "값의 흐름").
- 다른 빌드에서는 돌려 보지 못했다(이 빌드 하나뿐이다) [추정: 함수가 다시 컴파일되면 서명이 깨질 수 있다. 셋 가운데 둘이면 된다].

**서명을 다시 뽑는 법**(게임이 업데이트되어 `uv run srkit locate` 에 "안 맞음" · "여러 번"이 나올 때): 새 빌드에서 그 전역의 주소를 알아낸 뒤
(맞은 서명이 하나라도 있으면 그것이 낸 주소다) `uv run srkit sig-mine <RVA>` 를 돌린다. 치트 명령 처리 함수 밖의 코드에서, 한 번만 맞는
가장 짧은 서명(명령 셋 · 정해진 바이트 여덟 개 이상)을 함수별로 낸다. 서로 다른 함수의 것 셋을 골라 `native/srtoybox/locate.cpp` 의 표 `STATE` 에
옮기고, 이 표와 `tests/test_toybox_game.py` 의 기대값을 고친다.

**자동 테스트의 설치본 대조는 빌드에 묶여 있다.** `tests/test_toybox_game.py` 의 `BUILD_21347933_STAMP`(실행 파일의 TimeDateStamp)와
`tests/test_sigmine.py` 의 같은 값이 설치된 파일과 다르면, 값 대조뿐 아니라 요구 3 의 테스트(서명마다 한 번만 맞는다 · 치트 함수 밖이다 ·
서로 다른 함수다 · 치트 코드에서 읽은 값과 같다)도 **조용히 건너뛴다.** 게임이 업데이트되면 `uv run srkit locate` 로 먼저 보고(이 명령은 빌드를
가리지 않는다), 서명을 다시 뽑은 뒤 그 상수와 기대값을 새 빌드의 것으로 고쳐야 테스트가 다시 돈다.
값 묶음의 기대값(`BUILD_VALUES`)과 치트 본문에서 읽는 대조(`tests/toybox_cheat_oracle.py` 의 `values`)도 같은 상수에 묶여 있다.

### 새 찾기 — 값을 읽고 쓰는 자리 (3단계 1 (나)부터)

돈 · 물자 탭과 최소 유지가 쓰는 자리다. 상태 묶음과 같은 규칙의 서명으로 찾는다 — **내장 치트와 무관하다.** 여기서는 주소뿐 아니라
**구조체 안의 자리와 간격**(상수)도 서명이 읽어 낸다: `[u32]` 는 4바이트 상수, `[u8]` 은 1바이트 상수다. 제품 코드에는 자리가 적혀 있지 않다.

자동 테스트가 본다. 쓰는 물자 표의 셋째는 `sig-mine` 이 낸 것에서 가운데 명령 `imul rcx, rdx, 150h` 의 상수를 손으로 구멍으로 바꿨다 — 재고의 간격이
바뀌어도 함께 깨지지 않게.)

- **읽어 낸 값이 말이 되는지도 본다**(`locate_values`): 포인터는 쓸 수 있는 자료 구역 안 / 자리는 0 보다 크고 `0x100000` 보다 작다 / 간격은 0 이 아닌
  4 의 배수(칸이 float 다) / 국고 칸(8바이트)과 재고 칸들(4바이트 × 12)이 겹치지 않는다. 하나라도 아니면 "못 찾았다"다.
- **자리의 정렬도 본다**(3단계 1 (다)부터): 세계 자료 포인터의 주소와 국고 칸은 8 의 배수(포인터 · double), 두 표의 첫 칸은 4 의 배수(float)여야 한다.
  서명이 엉뚱한 바이트를 읽어 낸 경우를 거르려는 것이다. 까닭은 `세계 자료 포인터: 찾은 주소가 8 의 배수가 아닙니다` 꼴이다.
- **두 묶음이 겹치지 않는지도 본다**(`locate_fits`, 3단계 1 (다)부터): 세계 자료 포인터의 8바이트가 상태 묶음의 전역 일곱의 자리와 겹치면 값 묶음을 버린다
  (`세계 자료 포인터: 찾은 주소가 <그 전역> 의 자리와 겹칩니다`). 게임이 뜰 때의 ToyBox 와 `srkit locate` 가 같은 함수로 본다. 상태 묶음은 그대로 쓴다.
  build 21347933 의 값(`0x1af5868` · `+0x14B88` · `+0x14DA4` · `+0x18`)은 이 대조를 모두 지난다 [확인: 정적 — 자동 테스트] · [확인: 실행 — 로그의 `값을 씁니다 (…)`].
- **못 찾으면 돈 · 물자 탭만 꺼지고 최소 유지가 쉰다.** 탭에 까닭 한 줄이 보이고(`이 게임 판에서는 쓸 수 없습니다 (…)`), 내장 치트로 되돌아가지 않는다. 다른 기능은 그대로다.
- **재고의 칸 수 12 는 상수다**(`STOCK_SLOTS`). 코드에서 한 가지 꼴로 읽어 낼 자리가 없다(고리의 끝 검사가 곳마다 다르다). 근거는 둘이다 [확인: 정적]:
  치트 `products` 의 본문이 `+0x14DA4 + 0x150·i` 를 `i` = 0 … 11 로 펼쳐 놓았고("쓰는가" 검사도 12번), 치트 밖의 코드(`0x69fdab`)가 물자 번호를
  `cmp eax, 0Bh` / `ja` 로 거른 뒤 재고 칸으로 간다. 값을 읽을 때마다 12칸이 모두 유한한 수인지로 거른다.
- **서명의 문맥**: 국고의 세 자리는 같은 기준 레지스터에서 지역 객체의 다른 필드(`+4` 의 인덱스, `+0x14B48` 의 인구 등)도 읽는다. 재고의 세 자리는
  `imul r, r, 150h` 뒤에 지역 객체 + `14DA4h` 를 읽거나 쓴다. 쓰는 물자 표의 세 자리는 `[rip]` 로 읽은 세계 자료 포인터에 `imul r, r, 84h` 한 것과
  `+18h` 를 더해 float 를 읽는다(둘은 바로 `comiss` · `jbe` — "0 보다 큰가").

**상수를 읽어 내는 서명을 다시 뽑는 법**: `uv run srkit sig-mine --offset <상수> [<둘째 상수>]`. 첫 상수를 4바이트로 든 명령에서 시작해, 둘째 상수가
그 뒤 명령 넷 안에 나오는 자리만 본다.

```
uv run srkit sig-mine 1af5868                # 세계 자료 포인터(주소)
uv run srkit sig-mine --offset 14b88         # 국고 칸
uv run srkit sig-mine --offset 150 14da4     # 재고: 간격, 첫 칸
uv run srkit sig-mine --offset 84 18         # 쓰는 물자 표: 간격, 첫 칸
```

- 후보마다 그 명령들이 함께 나온다. **값만 우연히 같은 코드가 섞여 나오므로 명령을 보고 뜻이 맞는 것만 고른다.** `--offset 84 18` 이 특히 그렇다 —
  다른 구조체의 `+84h`, 스택의 `+18h`, 표의 첫 칸이 아니라 줄 안의 `+18h` 를 든 코드가 섞여, 후보가 나온 함수 25개 가운데 뜻이 맞는 것은 4개였다.
  맞는 것은 `[rip]` 로 읽은 세계 자료 포인터에 `imul r, r, 84h` 와 `+18h` 를 더해 float 를 읽는 것이다.
- **`sig-mine` 이 빼는 치트 코드는 12곳이다**: 명령 처리 함수(`0x522330 – 0x5284fd`)와, 치트 코드에서만 `call` 로 불리는 함수 11개
  (`0x51d370` · `0x51d3c0` · `0x51d860` · `0x51e110` · `0x51e3a0` · `0x51e640` · `0x51ea70` · `0x51ed50` · `0x51f0b0` · `0x528510` · `0x6f7100`).
  치트 문자열은 있는데 그것을 쓰는 함수를 못 찾으면 뽑지 않고 멈춘다. 상태 묶음의 서명 21개도 모두 그 밖이다(자동 테스트).
- 고른 서명은 `native/srtoybox/locate.cpp` 의 표 `VALUES` 에 옮기고, 이 표와 `tests/test_toybox_game.py` 의 `BUILD_VALUES` 를 고친다.
  `tests/toybox_cheat_oracle.py` 의 `values` 는 치트 `treasury` · `products` 의 본문에서 같은 값을 읽어 대조한다(치트 코드가 남아 있는 빌드에서만).
- **올라와 있는 게임에서도 열두 개가 모두 맞는다** [확인: 실행] — 화면 밖 게임과 Steam 으로 띄운 게임(Steam 오버레이의 훅이 함께 돈다)의 로그에
  `값을 씁니다 (국고 +0x14B88, 재고 +0x14DA4 간격 0x150 × 12)`. 상태 묶음과 값 묶음을 합쳐 찾는 데 47 ms 였다(네 번 모두. 로그의 `N ms` 는 두 묶음을 합친 시간이다).

### 옛 찾기 — 치트 명령 처리 함수와 그 둘레 (전환 기간에만)

아직 내장 치트로 도는 기능의 직접 실행이 쓰는 셋이다. `"cheat allowcheats"` 문자열을 닻으로 찾는다. 3단계의 마지막 묶음에서
직접 실행 · 글쇠 방식과 함께 지운다([10](10-toybox.md)).

| 찾을 것 | 절차 |
|---|---|
| 명령 처리 함수 | `"cheat allowcheats\0"`(읽기 전용 자료에 1개) → 그것을 가리키는 `lea r,[rip+d]`(1곳) → 그 자리가 든 함수 표 항목 → chained unwind 의 뿌리 |
| 옵션 묶음 | 함수 머리(0x60 바이트 안)의 `83 0D d32 40` |
| `this` | 함수를 부르는 `E8 rel32`(1곳) 바로 앞의 `48 8D 0D d32` |

대조 — 하나라도 어긋나면 "못 찾았다"이고, 내장 치트로 도는 기능은 글쇠 방식으로 동작한다(게임 상태 읽기에는 영향이 없다):

1. 닻 문자열이 1개이고 그것을 쓰는 자리가 1곳이다.
2. 함수 머리에 `or …,40h` 가 있다.
3. 함수를 부르는 곳이 1곳이고 바로 앞이 `lea rcx,[rip+d]` 다.
4. 찾은 주소가 모두 이미지 안에 있다.

## 이번에 알게 된 치트의 사실 [확인: 정적]

- `cheat damage` 는 줄 전체가 `cheat damage` 여야 맞는다. `cheat damage 5` 처럼 인자를 붙이면 영영 맞지 않는다.
- `cheat trumpme` 는 번갈아가 아니라 난수의 한 비트로 부호를 골라 ±$1 T 를 더한다.
- `cheat depopulate` 는 인구에 1 을 쓴다.
- 인자를 받는 지역 치트는 인자가 0 이면(주지 않으면) 전역 객체의 `+0x10` 이 가리키는 지역을 쓴다 — "지도에서 고른 지역"으로 보인다 [추정].
- 치트 허용 비트를 검사하는 25곳 가운데 19곳은 바로 뒤의 Steam 업적 호출(`"ACH%03d"`)을 건너뛴다. 치트를 켠 판에서는 그 업적들이 주어지지 않는 것으로 읽힌다 [추정: 실행해 본 것이 아니다].

## 보지 않은 것

- 멀티플레이 로비에서 멀티플레이 표시가 1 이 되는지(멀티플레이는 띄우지 않았다).
- 불러온 저장 · 시나리오 판 · 다른 나라에서 값의 흐름이 같은지(2030 - 세계 샌드박스와 캠페인의 독일에서만 봤다).
- 날짜를 넘기는 계산이 어느 스레드에서 도는지, 게임이 명령 처리 함수를 부르기 전후에 무엇을 잠그는지.
